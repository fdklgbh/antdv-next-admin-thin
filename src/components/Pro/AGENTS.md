# Pro 组件修改约束

本目录是跨页面复用的基础组件，修改会影响所有使用方。默认将其视为稳定 API：未经用户明确确认，不得修改本目录中的组件、测试或类型。

## 允许修改的情形

只有满足以下任一情形，才可提出修改：

1. 用户明确要求新增、调整或修复某个 Pro 组件能力。
2. 组件存在可复现的缺陷、交互问题、无障碍问题或安全问题。
3. 现有组件无法通过公开 props、slots、事件或组合式函数实现需求，且扩展点方案会影响多个调用方。
4. 项目依赖或全局主题升级造成 Pro 组件兼容性回归。
5. 本次任务明确涉及 Pro 组件的公共契约、类型、测试或文档。

页面专属布局、样式和业务逻辑应优先留在调用页面；仅影响单个业务域的定制不得进入 Pro 组件。

## 修改前确认

开始修改前，必须先向用户说明：

- 需要修改的组件和文件范围
- 现有能力为何不足，或缺陷如何复现
- 拟修改的公开 props、slots、事件、类型和行为
- 对现有调用方、主题、权限和构建产物的影响
- 替代方案以及不修改 Pro 组件时能否满足需求
- 计划执行的验证命令和需要手工检查的场景

用户明确确认后才能修改。若需求含义不清、影响面无法评估或确认范围发生变化，必须重新说明并获得确认。

## 兼容性原则

- 默认保持现有 props、slots、事件、类型和默认行为向后兼容。
- 不得删除或重命名公开 API；确需废弃时先提供兼容期和迁移说明。
- 新增能力优先通过可选配置扩展，不用业务分支污染通用组件。
- 不得把单个页面的业务字段、权限码、接口地址或文案写死在 Pro 组件中。
- 修改公共契约时同步更新相关类型、测试和使用示例，并检查所有调用方。
- 不借机重构无关组件、统一格式或升级依赖。

## 完成后的验证

至少执行 `pnpm run type-check`、`pnpm run lint` 和相关单元测试；涉及构建配置、样式或公共契约时执行 `pnpm run build`。修改表格、表单、弹窗或上传组件时，还要检查权限、空态、加载态、错误态、暗色主题和窄屏表现。

如果命令因环境限制无法执行，必须明确说明失败原因和未验证范围，不能视为通过。

## 需要用户确认的例外

紧急缺陷修复也应在动手前说明问题和拟修复范围。只有用户明确授权“直接修复”时，才可先实施、后补充验证说明；不得自行扩大范围。
